## 用户确认公告后的执行顺序

1. 重新 fetch 三个仓库，检查 main 没有新的相关改动，核对候选代码与公告、版本号一致；若公告需要修改，先同步公告文件及 CHANGELOG。
2. 推送 API 与管理后台 feature 分支，按现有 CI 进入预发；串行确认 API/market 与后台的配套版本，避免同仓库其他 feature 构建覆盖共享 staging 镜像。
3. 预发通过后合入并推送 API main，CI 构建 API/market 并按现有 SSH rollout 上线。新增两列按启动幂等升级，旧行为空，未改账号迁移或旧投稿归属。
4. 合入并推送管理后台 main；随后推送客户端/官网候选版本到 main，部署网站分享预览。核验网页脚本、JPEG Content-Type、/s 路由、官网访问 ICC 的跨域响应及后台场景展示。
5. 创建 v0.6.2 标签并推送，触发 release.yml；CI 从 CHANGELOG 提取公告，生成正式安装包、原始 minisign 签名、latest.json，同步更新服务、R2 与既有下载渠道。
6. 确认正式 Release 资产、签名、镜像下载与旧客户端检查更新正常，再发布用户通知；是否在公告后台另发通知按用户审阅后的发布安排执行。
7. 发布完成后将内部状态更新为已发布，按 release-workflow 归档本版本已完成的开发计划与交接；未完成的登录计划继续保留。

发布依据：[release-workflow](../../.skills/shared/release-workflow/SKILL.md)、现有 release.yml/docs.yml，以及 API/管理后台的 Docker CI 流程。用户本次明确要求先审阅公告，因此本轮仅完成本地准备。
