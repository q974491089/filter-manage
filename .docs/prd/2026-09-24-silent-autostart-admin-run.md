# 静默自启 + 管理员运行 PRD

**状态**: 草稿
**创建于**: 2026-09-24
**涉及端**: 前端（React/TS） / 客户端 Rust（Tauri） —— 服务端不涉及

## 背景

当前应用已有"开机自启"开关（`AppSettings.autostart`，通过 `tauri_plugin_autostart` 写入 HKCU 注册表 Run 项，注册时 args 为 `None`）。存在两个痛点：

1. **开机自启会弹出主窗口**：随系统启动时，应用像手动打开一样弹出主窗口，打断用户开机流程。作为一个后台运行、按方案/进程自动切换颜色的工具，用户期望它**开机时静默进托盘**，不弹窗。
2. **缺少管理员运行能力**：NVIDIA 颜色设置、ICC 安装/应用、进程监听（读取以管理员运行的游戏进程）等核心操作在无管理员权限时可能失败或不完整。用户希望能在设置里一键把软件切换为"以管理员身份运行"，且**持久生效**（以后每次启动都是管理员）。

两个需求叠加还引出一个 Windows 平台约束：**标准注册表 Run 自启项无法静默启动需要管理员权限的程序**（要么被系统拦截、要么开机弹 UAC）。经调研，Wallpaper Engine 等应用的做法是用 **Windows 计划任务（Task Scheduler）+ 登录触发 + 最高权限** 实现管理员级的开机静默自启且无 UAC —— 本 PRD 采用此方案。

## 目标

1. 开机自启动时，应用**静默进系统托盘**，不弹出主窗口；手动双击打开时行为不变（正常显示窗口）。
2. 设置中新增"以管理员身份运行"勾选项，勾选后经用户确认，应用以管理员权限重启并**持久**（以后每次启动都是管理员），取消勾选可恢复。
3. "管理员运行"与"开机静默自启"能**同时成立**：开机时静默进托盘 + 以管理员权限运行 + 全程无 UAC 弹窗（通过计划任务实现）。
4. 各开关切换/关闭后不残留（计划任务、注册表 Run 项、兼容性标志互斥且可清理干净，不会双重自启）。

## 范围

### 前端（React/TS）
- `AppSettings` interface 新增 `run_as_admin: boolean` 字段（`App.tsx` / `SettingsModal.tsx` / `ConfigManager.tsx` 三处的 interface 需同步）。
- `SettingsModal` 常规设置 tab：
  - 保留现有"开机自启"开关。
  - 新增"以管理员身份运行"勾选项。勾选时弹出**确认弹窗**，说明"将以管理员权限重启应用，并在之后每次启动都以管理员运行"，用户确认后调用后端命令；取消勾选时同样确认后调用后端关闭。
  - 触发后由后端重启应用（前端给出"即将重启"提示）。
- 文案与交互遵循 `DESIGN.md`；新增控件补齐 `data-components` / `data-name` 属性。

### 客户端 Rust（Tauri，src-tauri）
- `config.rs`：`AppSettings` struct 新增 `run_as_admin: bool`（`#[serde(default)]`，默认 `false`）。
- `lib.rs`：
  - autostart 插件注册改为带**静默标记参数**（如 `Some(vec!["--silent"])`），使注册表 Run 项启动时带该参数。
  - `setup` 中检测启动参数：带静默标记 → 窗口保持隐藏（仅托盘）；否则正常显示窗口。
  - 启动时的提权逻辑：若 `run_as_admin==true` 且当前进程未提权（手动启动场景）→ 自提权重启。
- 新增管理员/自启机制模块（如 `admin.rs` 或扩展现有 autostart 命令），封装：
  - 判断当前进程是否已提权（`is_elevated`）。
  - 自提权重启（`ShellExecute` + `runas`，经 `windows`/`windows-sys` crate 或复用现有依赖）。
  - Windows 计划任务的创建/删除（登录触发 + 最高权限 + 当前登录用户上下文 + 仅登录时运行），用于"管理员 + 自启"组合。
  - 兼容性标志（可选，`AppCompatFlags\Layers` 的 `RUNASADMIN`）——仅在最终方案需要"手动双击也提权"时使用；优先用自提权逻辑实现。
- 新增/调整 Tauri 命令：`set_run_as_admin(enabled)`、`is_running_as_admin`、以及让现有 `enable_autostart`/`disable_autostart` 感知 admin 模式（在"注册表 Run 项"与"计划任务"之间互斥切换）。
- `tauri.conf.json`：主窗口初始 `visible: false`（配合 setup 里按启动来源决定是否 `show()`，避免非静默启动时的窗口闪现）。

### 自启 × 管理员 行为矩阵（本次要实现的核心逻辑）

| 自启 | 管理员 | 开机启动机制 | 手动双击 |
|------|--------|--------------|----------|
| 关 | 关 | 无 | 正常显示窗口，非提权 |
| 开 | 关 | 注册表 Run 项 + `--silent` → 静默进托盘 | 正常显示窗口，非提权 |
| 关 | 开 | 无 | 自提权（一次 UAC）后显示窗口 |
| 开 | 开 | 计划任务（登录触发 + 最高权限）→ 静默进托盘且已提权，**无 UAC** | 自提权（一次 UAC）后显示窗口 |

> 注册表 Run 项与计划任务**二者互斥**：任一时刻只允许一种开机启动机制存在，切换 admin 模式时必须清理另一种，避免开机被启动两次。

## 非目标

- 不做"用户未登录也运行"（whether-user-is-logged-on），那需要存储账户密码，风险高；只做"登录时运行 / 仅当前用户登录时"。
- 不修改/关闭系统级 UAC 设置（调研中出现过"关 UAC"做法，明确拒绝，属危险且影响全局安全）。
- 不改动 macOS/Linux 行为（本项目仅 Windows）。
- 不做通用权限管理框架，只覆盖本 PRD 描述的开关。
- 不改动现有颜色方案/进程监听/更新等既有功能逻辑（除非静默启动路径必须调整其触发时机）。

## 涉及端与分工提示

- **跨端功能**：前端（设置 UI + interface 字段）+ 客户端 Rust（自启机制、提权、计划任务、窗口可见性）。服务端不涉及。
- **后端为主**：核心复杂度在 Rust 侧（计划任务、提权、启动参数分流）；前端改动较轻（一个开关 + 确认弹窗 + 一个字段）。
- **文档同步**：后端新增/变更命令后需按 `.rules/docs.md` 同步 `.docs/api/*.md`。

## 验收标准

- [ ] **自启关闭**：行为与现状一致，无回归。
- [ ] **自启开启（非管理员）**：重启电脑并登录后，应用随登录启动，**不弹主窗口**、仅出现托盘图标；已有的"启动时应用默认方案"行为仍生效；双击托盘或选"显示主窗口"能正常打开窗口。
- [ ] **手动双击（非管理员模式）**：正常弹出主窗口。
- [ ] **勾选"以管理员身份运行"**：弹出确认框说明将重启为管理员；确认后应用以管理员权限重启（任务管理器"以管理员身份"列显示"是"）；`run_as_admin` 持久化到 `app.json`，下次启动仍为管理员。
- [ ] **管理员 + 自启 同时开启**：重启电脑并登录后，应用**静默进托盘、以管理员权限运行、全程无 UAC 弹窗**（经计划任务）。
- [ ] **管理员模式下手动启动**：出现一次 UAC 提示（符合预期），确认后提权运行。
- [ ] **取消"以管理员身份运行"并重启**：恢复非管理员运行；计划任务被删除；若自启仍开启则自动回退到注册表 Run 项静默自启。
- [ ] **无残留 / 不双启**：任一开关组合切换后，注册表 Run 项、计划任务、兼容性标志三者状态互斥且正确；开机不会被启动两次。
- [ ] **配置一致性**：提权与非提权启动读写的是同一份 `app.json`（同用户 `%APPDATA%\filter-manage`），设置不丢失。

## 已知风险 / 依赖 / 坑

- **配置计划任务本身需要提权**：创建/删除"最高权限"计划任务要求应用当时已提权 → 首次开启"管理员运行"必然过一次 UAC 来完成配置。这是可接受的一次性成本，需在确认弹窗里向用户说明。
- **计划任务参数必须正确**：调研（MS Q&A）显示任务的账户上下文若设成 `Administrators` 组而非具体登录用户，仍会弹 UAC。必须按"当前登录用户 + 仅在用户登录时运行 + 最高权限 + 登录触发"配置。
- **两种自启机制互斥**：注册表 Run 项与计划任务同时存在会导致开机启动两次；切换 admin 模式时必须清理另一种。`tauri_plugin_autostart` 在 admin 模式下应停用其注册表写入，改由计划任务承担。
- **自提权后避免双实例**：自提权（`ShellExecute runas`）拉起新进程后，原非提权进程要干净退出；需与已有 `tauri_plugin_single_instance` 协调，避免冲突或"提权实例被单例逻辑挡回"。
- **静默启动时的方案应用时机**：需确认"启动时应用默认方案"目前由前端（App.tsx 加载后 invoke）还是后端触发。Tauri 中隐藏窗口仍会创建 webview 并运行前端，故前端逻辑理论上照常执行——但需在实现阶段验证隐藏启动路径下方案确实被应用；若依赖窗口可见则要改为后端触发。
- **卸载残留**：安装包卸载时应清理计划任务/Run 项（本 PRD 可先保证应用内关闭开关能清理干净，安装器层面的清理视情况列为后续）。
- **平台/构建约束**：依赖安装与构建必须在 **Windows PowerShell** 执行（WSL 缺原生库，见项目 dev 环境约定）；开机、UAC、计划任务等真实行为**无法在 WSL 验证**，只能在 Windows 侧手动重启测试。
- **依赖评估**：计划任务可用 `schtasks.exe`（命令行，注意窗口闪现与转义）或 Task Scheduler COM API（`windows` crate）；提权判断/`ShellExecute` 需要 `windows`/`windows-sys`。实现阶段确认现有 `Cargo.toml` 是否已含所需 feature，避免新增重依赖。
